# Smart City Visibility, Placement, and Asset Expansion Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Fix the current Smart City asset/ecology visibility and placement problems in Blender, then expand the asset set enough to produce a cleaner, more convincing demo scene.

**Architecture:** Keep the current `iCity/smart_city/` module split and avoid rewriting the generated-style iCity core. Treat this as a second-phase stabilization plan: first strengthen geometry/layout validation, then replace rough placement logic with demo-stable placement rules, then add a small curated batch of new assets that fit the same placement pipeline.

**Tech Stack:** Blender 4.x, Python `bpy`, existing `iCity` add-on scene data, JSON-style manifest patterns already used in `smart_city`, Python `unittest`, Markdown docs.

---

## 1. Problem Summary

Current Blender feedback shows four concrete gaps:

- Procedural streetlights are generated, but they can appear inside the city instead of along plausible road edges.
- Lake, road loop, and traffic/crowd blocks can be technically outside the protected city radius but still end up hidden behind buildings in the main viewport or demo framing.
- Current placement uses city bounding approximations, not actual visual frontage or road-aligned placement.
- Asset variety is still too narrow for a strong demo; the module currently relies mostly on material swaps, streetlights, lake/water, and simple traffic proxies.

The code already passes basic regression tests, but those tests only confirm:

- layout does not invade the city safety radius
- texture lookup works for numbered duplicate files

They do not yet confirm:

- objects are visible in the final demo
- streetlights stay outside dense building regions
- generated assets sit near plausible road-side or ecology-side bands
- placement remains stable across several city seeds

This plan focuses on those missing guarantees.

## 2. Scope

This plan covers:

- Asset placement logic for `asset_extension.py`
- Ecology and traffic layout logic for `ecology_common.py`, `ecology_water.py`, and `ecology_traffic.py`
- Additional validation tests for placement geometry
- A modest asset expansion set under the existing `smart_city` workflow
- Documentation and Blender validation steps for the team

This plan does **not** cover:

- full true-road extraction from arbitrary iCity geometry
- physics-based traffic simulation
- marketplace/template system work
- major refactors of base iCity add-on internals

## 3. Root Cause Analysis

### 3.1 Streetlight placement

Current streetlights are generated by:

- `asset_extension.get_city_bounds()`
- `asset_extension.perimeter_positions()`

The current strategy is:

- estimate one city center and one radius
- create a rectangle around that radius
- distribute lights evenly along the rectangle perimeter

That means the placement logic knows the **approximate city footprint**, but not:

- where roads are
- where dense building blocks are
- which side is the best side for demo framing

As a result, lights can land in visually bad positions even if they are mathematically outside part of the raw city bounds.

### 3.2 Ecology and traffic visibility

Current ecology/traffic placement is controlled by:

- `ecology_common.get_city_bounds()`
- `ecology_common.compute_layout()`
- `ecology_traffic.generate_traffic_system()`
- `ecology_water.create_lake()` / `create_river()` / `create_terrain()`

The current strategy is stronger than before because it enforces a safety buffer, but it still assumes:

- any direction away from the city center is equally good
- being outside a protected radius is enough

That is not enough for demo use. A block can be outside the city and still end up visually hidden behind buildings depending on the main view direction.

### 3.3 Asset variety

The current asset system proves the concept, but it still lacks enough visible supporting assets to make the scene feel intentionally built. The biggest gap is not huge model count; it is a lack of a few strong support categories:

- roadside fillers
- ecology-side fillers
- traffic presentation variants

## 4. Target Outcome

After this plan is implemented, the Blender demo should behave like this:

- Streetlights appear in an outer roadside band rather than inside the city mass.
- Lake/river and traffic loop appear in a predictable side zone that is intentionally visible.
- Crowd path sits around the ecology block without clipping into the city.
- A small set of additional props makes the generated result look fuller without requiring heavy imported assets.
- The team can run a repeatable Blender checklist and quickly tell whether the scene is acceptable.

## 6. Implementation Strategy Options

### Option A: Demo-safe directional placement

- choose one deterministic “show side” based on seed or city frontage
- place lake, traffic loop, and crowd ring in separate bands on that side
- place streetlights in an exterior roadside ring that excludes the core city box

Pros:

- low implementation risk
- easiest to test
- best fit for classroom demo

Cons:

- not true road extraction

### Option B: Boundary-aware filtered placement

- start from current bounding logic
- sample candidate points around the city
- reject points that fall inside the dense city box or too near building mass
- keep only the clean outer band

Pros:

- more robust than pure formulas
- still lighter than true road parsing

Cons:

- more helper logic
- still approximate

### Option C: Real road-derived placement

- inspect `ICity Road` and related geometry
- derive edges/lanes from actual road objects
- place lights and traffic directly from real road data

Pros:

- highest realism

Cons:

- highest risk
- depends heavily on iCity scene internals

### Recommendation

Use a hybrid of **Option A + Option B**:

- directional demo-side layout for ecology and traffic
- filtered outer-band placement for streetlights and future roadside props

This gives the best reliability for the current course timeline.

Planned helper shape in `asset_extension.py`:

```python
def point_in_city_core(point: Vector, center: Vector, radius: float) -> bool:
    local_x = abs(point.x - center.x)
    local_y = abs(point.y - center.y)
    return local_x < radius * 0.78 and local_y < radius * 0.58
```

```python
def filtered_perimeter_positions(center: Vector, radius: float, settings) -> list[tuple[Vector, float]]:
    candidates = perimeter_positions(center, radius + max(settings.streetlight_offset, 4.0), settings)
    filtered = [(point, rotation) for point, rotation in candidates if not point_in_city_core(point, center, radius)]
    return filtered[: max(1, settings.streetlight_count)]
```

Then update the generation operator to use the filtered helper instead of raw perimeter points.

```python
def choose_demo_axes(seed: int) -> tuple[Vector, Vector]:
    angle = math.radians((seed * 41) % 360)
    direction = Vector((math.cos(angle), math.sin(angle)))
    side = Vector((-direction.y, direction.x))
    return direction, side
```

```python
def compute_demo_offsets(city_radius: float, settings, lake_radius_x: float, lake_radius_y: float) -> dict:
    safe_buffer = max(6.0, min(settings.terrain_margin * 0.22, settings.lake_radius * 0.55))
    traffic_outer = max(settings.traffic_loop_radius_x, settings.traffic_loop_radius_y) + settings.road_width * 0.5
    return {
        "safe_buffer": safe_buffer,
        "lake_distance": city_radius + max(lake_radius_x, lake_radius_y) + safe_buffer,
        "traffic_distance": city_radius + traffic_outer + max(4.0, safe_buffer * 0.72),
    }
```
