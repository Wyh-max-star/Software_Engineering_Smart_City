# ICity Layout Control Design

## 1. 文档目的

本文档定义课程项目中“布局控制”模块的产品目标、功能边界、数据模型、拓扑处理规则、Blender/iCity 接入方式、草图识别流程、测试策略和分阶段实现方案。

本设计首先解决当前 iCity 编辑体验中的核心问题：

- 用户难以在完整城市模型中准确选择 `ICity Base` 的顶点、边和面。
- `Assign Road` / `Remove Road` 只切换已有边的道路属性，不负责真正增删拓扑。
- 手工使用 Knife、Extrude、Fill、Dissolve 等 Blender 网格操作容易破坏街区面。
- 新增边和面后，用户还需要手动补充 iCity 自定义属性。
- 当前界面不能直接查看道路节点坐标、连接关系和拓扑错误。
- 草图布局与手动布局缺少统一的数据入口。

布局控制模块应将这些底层操作统一封装为一个可查看、可编辑、可校验、可应用的二维道路图工作流。

## 2. 背景与现有系统

### 2.1 iCity 的基础布局表示

`iCity Start` 从 `assets/ICity start.blend` 加载基础场景，并将 `ICity Base` 作为城市编辑对象。

当前系统使用一张 Blender Mesh 同时表达：

- 顶点：道路端点、转折点或交叉点。
- 边：候选道路中心线。
- 面：道路围成的城市街区。
- 边属性：道路是否启用、道路宽度、道路类型等。
- 面属性：街区类型、程序化建筑类型、楼层数量等。

关键代码契约：

- `iCity/__init__.py:SNA_OT_Edit_City_D7Cab`：进入 `ICity Base` 编辑模式。
- `iCity/__init__.py:SNA_OT_Assign_Road_Deef9`：将选中边的 `Road del` 设为 `False`。
- `iCity/__init__.py:SNA_OT_Remove_Road_A2302`：将选中边的 `Road del` 设为 `True`。
- `iCity/__init__.py:SNA_OT_City_Apply_Dae66`：设置选中面的 `space type`、`Procedural index` 等属性。

`Road del` 的语义如下：

| 值 | 含义 |
|---|---|
| `False` | 边作为道路参与生成 |
| `True` | 边存在，但不作为道路生成 |

### 2.2 下游模块对布局的依赖

`traffic_extension.py` 从 `ICity Base` 读取：

- Mesh 顶点坐标。
- Mesh 边连接关系。
- 边属性 `Road del`。

随后将有效边组合为道路链，用于车辆路径生成。`pedestrian_extension.py` 复用同一道路图规划行人路径。

因此，布局控制模块的正式应用结果必须与 `ICity Base` 保持一致。只创建额外 Curve 或普通 Mesh，无法保证原始道路、建筑、交通和行人共同使用新布局。

## 3. 产品目标

### 3.1 核心目标

提供一个独立的 `ICity Layout Control` 面板，使用户可以：

1. 从当前 `ICity Base` 读取并查看道路节点、连接线和街区信息。
2. 使用坐标和节点 ID 精确修改道路图。
3. 添加、删除和移动节点。
4. 添加、删除和修改道路连接。
5. 自动处理交点、近邻节点、重复边、重叠线段和可选的共线合并。
6. 在应用前查看规范化结果、警告和错误。
7. 将确认后的布局统一应用到 `ICity Base`。
8. 从草图图像提取初始点线图，并进入相同的编辑与应用流程。

### 3.2 用户价值

用户不再需要直接执行以下 Blender 底层操作：

- 在复杂场景中选择微小顶点和边。
- 使用 `K`、`E`、`F`、Dissolve 等命令修改拓扑。
- 手工标记每条新道路。
- 手工恢复切割后街区面的城市属性。
- 自己判断两条视觉相交的道路是否在拓扑上真正连接。

### 3.3 非目标

第一阶段明确不实现：

- 类似专业 GIS/CAD 软件的完整交互式绘图系统。
- 真实交通法规、道路等级规划或车道级路口设计。
- 自动保证任意复杂街区都能被现有 Geometry Nodes 正确生成建筑。
- 在保留所有已有建筑自定义配置的前提下，对任意拓扑进行无损局部修改。
- 从彩色卫星图中可靠识别真实道路。
- 在草图识别后未经用户确认便直接覆盖当前城市。

## 4. 需求边界

### 4.1 必须支持

- 读取当前场景中的点和线坐标。
- 使用列表查看当前节点与道路。
- 通过结构化文本导入完整点线图。
- 修改节点坐标和道路端点。
- 添加和删除节点、道路。
- 检查无效引用、自环、零长度边和重复边。
- 合并距离小于阈值的近邻节点。
- 对相交道路创建交点并拆分线段。
- 对“点在线上”的情况拆分线段。
- 对完全重复和部分重叠的共线线段进行规范化。
- 提供可选的共线二度节点简化。
- 应用前展示变更摘要和问题列表。
- 将结果写入 `ICity Base` 并初始化必要属性。
- 提供撤销友好的 Blender Operator。

### 4.2 应当支持

- 从当前 `ICity Base` 重新载入，丢弃尚未应用的面板修改。
- 在 Blender 视图中显示布局预览对象。
- 在列表中选择节点或道路时，在预览中高亮对应元素。
- 自动检测封闭街区候选面。
- 对不适合建筑生成的街区给出警告。
- 支持 JSON 文件导入和导出。
- 支持黑白线稿草图识别。

### 4.3 可后续支持

- 直接在二维预览中点击绘制道路。
- 局部应用而不是整体重建。
- 道路级属性编辑，例如宽度、类型和人行道宽度。
- 街区级属性编辑，例如公园、程序化建筑和预设建筑。
- 更复杂的曲线道路表达。

## 5. 统一道路图数据模型

### 5.1 设计原则

手动输入、当前场景读取、JSON 导入和草图识别必须统一转换为同一种中间模型。后续校验、规范化、预览和应用不得因输入来源不同而重复实现。

建议建立不依赖 Blender 的纯 Python 模块：

```text
iCity/smart_city/layout_graph.py
```

### 5.2 核心结构

概念模型：

```python
LayoutGraph:
    nodes: dict[str, LayoutNode]
    edges: dict[str, LayoutEdge]
    blocks: list[LayoutBlock]
    metadata: dict

LayoutNode:
    id: str
    x: float
    y: float
    z: float
    source: str

LayoutEdge:
    id: str
    start_node_id: str
    end_node_id: str
    enabled_as_road: bool
    attributes: dict

LayoutBlock:
    id: str
    boundary_node_ids: list[str]
    attributes: dict
```

第一阶段的用户输入只强制要求 `nodes` 和 `edges`。`blocks` 可由系统从封闭道路环推导。

### 5.3 JSON 格式

建议支持以下格式：

```json
{
  "version": 1,
  "nodes": [
    {"id": "n0", "x": 0.0, "y": 0.0},
    {"id": "n1", "x": 20.0, "y": 0.0},
    {"id": "n2", "x": 20.0, "y": 15.0},
    {"id": "n3", "x": 0.0, "y": 15.0}
  ],
  "edges": [
    {"id": "e0", "start": "n0", "end": "n1"},
    {"id": "e1", "start": "n1", "end": "n2"},
    {"id": "e2", "start": "n2", "end": "n3"},
    {"id": "e3", "start": "n3", "end": "n0"}
  ]
}
```

节点使用稳定字符串 ID，而不是仅依赖列表下标。这样用户删除节点后，不会导致所有后续道路引用整体错位。

### 5.4 坐标约定

- 布局编辑使用 `ICity Base` 对象局部 XY 平面。
- 默认 `z = 0`，第一阶段不支持立交和多层道路。
- 从场景读取时，将世界坐标转换为 `ICity Base` 局部坐标。
- 应用时再由局部坐标构建 Mesh，避免对象 Transform 导致坐标混乱。
- 所有容差均以 Blender 世界单位解释，默认假设一单位近似一米。

## 6. 拓扑规范化

### 6.1 为什么必须规范化

用户输入和草图识别产生的是几何线段，但 iCity、交通和行人模块需要的是正确连通的道路图。视觉上相交并不等于拓扑上连接。

所有应用操作必须先执行：

```text
输入图
→ 基础校验
→ 节点吸附
→ 交点拆分
→ 重叠线段规范化
→ 重复边清理
→ 可选简化
→ 街区检测
→ 应用图
```

### 6.2 基础校验

拒绝或清理：

- 边引用不存在的节点。
- 边起点和终点相同。
- 两端距离小于最小道路长度。
- 节点坐标不是有限数字。
- 重复节点 ID 或重复边 ID。

错误必须阻止应用；可自动修复的问题应形成警告和修复摘要。

### 6.3 近邻节点合并

当两个节点间距小于 `merge_distance` 时，可视为同一路口。

规则：

- 默认阈值建议 `0.25`。
- 合并后重新连接所有关联边。
- 若合并产生自环，则删除自环。
- 若合并产生重复边，则删除重复边。
- 使用确定性规则选择保留 ID，例如优先保留场景原有节点，再按 ID 排序。

### 6.4 点在线段上

若节点 `P` 到边 `A-B` 的距离小于容差，且投影位于线段内部，则将：

```text
A-B
```

拆分为：

```text
A-P
P-B
```

这保证用户添加在道路中间的节点真正参与道路拓扑。

### 6.5 线段相交

若两条非共线边在内部相交：

```text
A-B 与 C-D
```

系统创建或复用交点 `X`，并拆分为：

```text
A-X
X-B
C-X
X-D
```

端点相交不应重复创建节点。多个交点落在同一线段时，按在线段上的参数顺序拆分。

### 6.6 重复和反向边

道路按无向边处理：

```text
A-B == B-A
```

完全重复道路只保留一条。若属性冲突，第一阶段阻止应用并要求用户处理，避免静默选择错误属性。

### 6.7 共线重叠线段

对于部分或完全重叠的共线道路：

```text
A---------C
     B---------D
```

规范化结果应使用所有关键端点拆分成不重复的最小线段：

```text
A-B
B-C
C-D
```

每个几何区间只保留一条道路边。

### 6.8 共线节点简化

当节点 `B` 满足以下条件时，可以将 `A-B` 和 `B-C` 合并为 `A-C`：

- `B` 的道路度数恰好为 2。
- `A`、`B`、`C` 在角度容差内共线。
- 两条道路属性一致。
- `B` 不是用户锁定节点。
- `B` 不是其他非道路信息的锚点。

该功能默认关闭或仅作为“优化布局”显式操作。无条件合并会删除有意义的路口和属性分界。

### 6.9 街区检测

规范化道路图后，需要检测由道路围成的封闭区域，作为 `ICity Base` 面候选。

建议采用平面嵌入图的半边遍历：

1. 对每个节点，将相邻边按极角排序。
2. 从每条有向半边出发，始终选择固定转向规则的下一条边。
3. 得到闭合环。
4. 根据有向面积排除外部无限区域。
5. 去重并生成街区候选。

第一阶段限制：

- 不支持立交。
- 交叉道路必须已拆分并共享交点。
- 对包含孔洞、复杂嵌套或自交的区域给出警告，不保证生成建筑。

### 6.10 街区形状质量检查

现有 iCity 建筑生成对面形状可能存在隐含限制。系统应至少检查：

- 面积是否大于最小值。
- 边长是否过短。
- 面是否自交。
- 面是否过窄。
- 面是否为凹多边形。
- 顶点数量是否过多。
- 三角形或高度不规则面是否可能无法生成建筑。

这些检查第一阶段只产生警告，不应未经验证便强制将所有街区转换为四边形。

## 7. Blender 用户界面

### 7.1 面板位置

在 `VIEW_3D > UI > ICity` 中新增独立面板：

```text
ICity Layout Control
```

不直接扩展生成式风格的原始 `ICity editor` 大段代码，避免难以维护和增加回归风险。

### 7.2 面板结构

建议分为五个折叠区。

#### A. Current Layout

- `Load From ICity Base`
- 当前节点数、道路数、街区候选数。
- 当前布局是否存在未应用修改。
- `Reset Draft`
- `Export JSON`

#### B. Nodes

使用 `UIList` 展示：

| ID | X | Y | 状态 |
|---|---:|---:|---|
| n0 | 0.00 | 0.00 | existing |

操作：

- Add Node
- Remove Node
- Duplicate Node
- 编辑 X/Y。
- 选择列表项时高亮预览节点。

删除有连接的节点时必须明确展示将同时删除的道路数量。

#### C. Roads

使用 `UIList` 展示：

| ID | Start | End | Road |
|---|---|---|---|
| e0 | n0 | n1 | enabled |

操作：

- Add Road
- Remove Road
- 修改起点和终点。
- 启用或关闭道路。
- 选择列表项时高亮预览道路。

#### D. Normalize & Validate

参数：

- Merge Distance
- Intersection Tolerance
- Minimum Edge Length
- Simplify Collinear Nodes

操作：

- `Validate`
- `Normalize Draft`

结果：

- 错误列表。
- 警告列表。
- 将合并多少节点。
- 将创建多少交点。
- 将拆分多少道路。
- 将删除多少重复边。
- 检测到多少街区。

#### E. Import & Apply

- JSON 文本输入或文件选择。
- 草图图像文件选择。
- `Parse JSON`
- `Extract From Sketch`
- `Apply To ICity Base`

`Apply` 必须显示确认信息：

```text
当前 ICity Base 将被整体重建。
节点: 8 -> 12
道路: 10 -> 16
街区: 3 -> 5
```

### 7.3 布局预览

建议创建独立预览集合：

```text
ICity Layout Preview
```

预览包含：

- 节点：Empty 或轻量圆点对象。
- 道路：Curve 或轻量 Mesh 线段。
- 错误：红色。
- 警告：黄色。
- 正常道路：蓝色。
- 当前选中元素：高亮颜色。

预览只用于表达草稿，不被交通、行人或 Geometry Nodes 消费。应用或清理时统一删除。

第一阶段不要求用户直接在预览对象上点击编辑，但应保证用户能够直观看到输入图与规范化结果。

## 8. 从当前 ICity Base 读取布局

### 8.1 读取内容

`Load From ICity Base` 应读取：

- 对象局部坐标中的所有 Mesh 顶点。
- 所有 Mesh 边及其顶点索引。
- `Road del` 等已知边属性。
- 所有 Mesh 面及其已知城市属性。

每个读取元素记录来源索引：

```python
metadata = {
    "source_object": "ICity Base",
    "source_vertex_index": 3,
    "source_edge_index": 5
}
```

### 8.2 当前道路与候选边

界面应区分：

- 有效道路边：`Road del == False`。
- 非道路候选边：`Road del == True`。

不能只读取有效道路，否则用户无法查看和重新启用当前已有的候选边。

### 8.3 属性保留

从场景读取的边和面应尽量保存原属性。若规范化后某元素可以明确追踪到原元素，则继承属性；无法追踪时使用模块默认值。

## 9. 应用到 ICity Base

### 9.1 第一阶段应用策略

第一阶段建议采用“整体重建 `ICity Base` Mesh”：

1. 保存当前草稿和规范化结果。
2. 创建新的顶点列表。
3. 创建规范化后的边列表。
4. 根据街区检测结果创建面列表。
5. 使用 Blender Mesh API 重建 `ICity Base.data`。
6. 重建并初始化必要 Mesh Attributes。
7. 对可追踪元素恢复原属性。
8. 通知 `ICity Road` 等相关对象刷新。

该方案比直接模拟用户的 Knife、Dissolve 和属性设置操作更稳定、更易测试。

### 9.2 属性初始化

已从 Python 源码确认的关键属性包括：

边属性：

- `Road del`
- `street type`
- `Road lanes width`
- `side walk offset`

顶点属性：

- `offset`
- `crosswalk offset`

面属性：

- `space type`
- `Procedural index`
- `Floor count`
- `Floor count max`
- 以及 Park、Presets、Landscape 等相关属性。

实施前必须在 Blender 中检查 `ICity Base.data.attributes`，记录每个属性的：

- 名称。
- 数据类型。
- Domain：POINT、EDGE、FACE 或其他。
- 默认值。
- Geometry Nodes 是否强依赖该属性。

不能仅凭属性名称猜测类型和默认值。

### 9.3 默认策略

建议默认：

- 所有输入道路边：`Road del = False`。
- 由布局需要但不应生成道路的辅助边：`Road del = True`。
- 新街区：`space type = Procedural`。
- 其他道路和建筑属性：从一个已知可工作的模板边/模板面复制。

“从模板元素复制默认属性”比硬编码所有默认值更能兼容现有资源，但模板选择和缺失时的错误必须明确。

### 9.4 原对象身份

优先保留 `ICity Base` 对象本身，只替换或重建其 Mesh 数据，避免其他对象、Geometry Nodes 或脚本因对象名称和引用变化而失效。

### 9.5 撤销与恢复

- 应用 Operator 使用 `UNDO`。
- 应用前可选择自动导出当前布局 JSON 作为备份。
- 不创建隐藏回退布局或静默恢复逻辑。
- 若验证存在阻断错误，则拒绝应用。

## 10. 草图布局控制

### 10.1 输入约束

第一版草图识别面向简单道路线稿：

- 白色背景。
- 黑色或深色单线道路中心线。
- 道路交叉清晰。
- 尽量无文字、阴影和复杂纹理。

不承诺处理卫星图、真实地图截图或带宽度的复杂道路图。

### 10.2 处理流程

```text
读取图像
→ 灰度化
→ 二值化
→ 去噪
→ 骨架化为单像素中心线
→ 检测端点和交叉点
→ 沿骨架追踪节点之间的路径
→ 简化折线
→ 像素坐标转换为布局坐标
→ 生成 LayoutGraph
→ 执行统一规范化与验证
```

### 10.3 坐标转换

用户需要配置或确认：

- 图像对应的世界宽度或缩放比例。
- 原点位置。
- 是否翻转 Y 轴。
- 是否居中到当前城市。

草图识别结果只能进入草稿，不直接应用。

### 10.4 依赖策略

Blender 自带 Python 环境未必包含 OpenCV、scikit-image 等库。实施前需决定：

1. 使用可打包的纯 Python/轻量依赖实现有限识别。
2. 明确要求用户安装 OpenCV。
3. 在插件外提供预处理脚本，再由插件导入 JSON。

该选择涉及部署方式和课程演示稳定性，必须讨论确认后再实现，不能静默增加外部依赖。

## 11. 模块架构

建议文件结构：

```text
iCity/smart_city/
  layout_graph.py
  layout_normalization.py
  layout_blender_bridge.py
  layout_control.py
  layout_sketch.py
  docs/README_LAYOUT_CONTROL.md
```

职责：

| 模块 | 职责 |
|---|---|
| `layout_graph.py` | 数据模型、JSON 解析与导出、基础校验 |
| `layout_normalization.py` | 节点合并、交点拆分、重叠处理、街区检测 |
| `layout_blender_bridge.py` | 从 `ICity Base` 读取和应用布局 |
| `layout_control.py` | Blender PropertyGroup、UIList、Panel、Operator、预览 |
| `layout_sketch.py` | 图像到 LayoutGraph 的转换 |

纯图算法模块不得依赖 `bpy`，以便在普通 Python 单元测试中验证。

### 11.1 数据流

```text
ICity Base / JSON / Sketch
          ↓
      LayoutGraph Draft
          ↓
  Normalize + Validate
          ↓
   Normalized LayoutGraph
          ↓
  Preview / User Confirmation
          ↓
      ICity Base Mesh
          ↓
Road / Building / Traffic / Pedestrian
```

## 12. 错误处理

### 12.1 阻断错误

以下问题必须阻止应用：

- 未找到 `ICity Base`。
- 边引用不存在节点。
- 非有限坐标。
- 自交或重叠情况无法规范化。
- 无法创建有效 Mesh。
- 缺少 Geometry Nodes 必需属性且无法从模板复制。
- 当前处于不适合重建 Mesh 的 Blender 模式。

### 12.2 警告

以下问题允许用户确认后继续：

- 存在断头路。
- 存在没有形成街区的道路。
- 街区为三角形、凹多边形或过窄。
- 某些原有属性无法保留，已使用默认值。
- 草图识别创建了大量近邻节点。
- 应用将删除现有未被草稿包含的候选边。

### 12.3 禁止隐藏行为

模块不得：

- 静默删除无法理解的道路。
- 静默改变用户道路连接关系。
- 在验证失败时偷偷使用旧布局。
- 草图识别失败后自动生成演示道路。
- 未经确认覆盖当前 `ICity Base`。

## 13. 测试策略

### 13.1 纯 Python 单元测试

针对 `layout_graph.py` 和 `layout_normalization.py`：

- JSON 解析和序列化往返一致。
- 拒绝不存在节点引用。
- 删除自环和重复无向边。
- 合并近邻节点后连接关系正确。
- 点在线上时正确拆边。
- 两条线相交时创建一个共享节点。
- 多条线在同一点相交时只创建一个节点。
- 部分重叠线段被拆成不重复区间。
- 共线简化只删除度数为 2 的普通节点。
- 封闭矩形检测出一个街区。
- 带中间道路的矩形检测出两个街区。
- 开放道路图不生成街区。
- 外部无限区域不作为街区。

### 13.2 Blender 桥接测试

在可用的 Blender 测试环境中验证：

- 能读取 `ICity Base` 顶点、边、面和属性。
- 世界坐标与局部坐标转换正确。
- 应用后仍保留名为 `ICity Base` 的对象。
- 应用后 `Road del` Domain 和数据长度正确。
- 新道路可驱动 `ICity Road` 更新。
- 新街区可在支持的形状下生成程序化建筑。
- 交通和行人能读取新道路图。
- Undo 能恢复应用前布局。

### 13.3 手动验收

#### 场景读取

1. 运行 `iCity Start`。
2. 打开 `ICity Layout Control`。
3. 点击 `Load From ICity Base`。
4. 确认面板显示节点和道路数量。
5. 确认预览与当前道路图一致。

#### 精确编辑

1. 修改一个节点坐标。
2. 添加一条道路。
3. 删除一条道路。
4. 执行 Normalize 和 Validate。
5. 确认预览正确显示修改。

#### 交叉处理

1. 输入两条相交道路。
2. Normalize。
3. 确认自动创建交点并拆分成四条边。

#### 应用

1. 应用一个包含多个四边形街区的布局。
2. 确认道路生成。
3. 确认支持的街区生成建筑。
4. 确认交通和行人读取新道路。

#### 草图

1. 导入简单黑白道路草图。
2. 提取草稿。
3. 检查识别点线。
4. 手工修正后再应用。

## 14. 分阶段实施建议

### Phase 0：契约验证

目标：确认现有 iCity 对 Mesh 和 Attributes 的真实要求。

- 在 Blender 中导出 `ICity Base` 属性名称、类型、Domain 和默认值。
- 验证矩形、三角形、凹多边形等街区的建筑生成能力。
- 验证整体重建 Mesh 后 Geometry Nodes 是否仍正常工作。
- 验证从模板边和模板面复制属性的可行性。

Phase 0 完成前，不应实现完整应用逻辑。

### Phase 1：只读布局查看器

目标：让用户直观看到当前点线坐标和连接关系。

- 从 `ICity Base` 读取布局。
- 节点和道路 UIList。
- JSON 导出。
- 预览集合。
- 不修改场景布局。

该阶段风险低，并能立即缓解“看不到当前布局”的问题。

### Phase 2：手动点线编辑与规范化

目标：在草稿层完成可靠的点线编辑。

- 添加、删除、修改节点和道路。
- JSON 导入。
- 基础校验。
- 近邻合并。
- 交点拆分。
- 重复和重叠线段处理。
- 街区检测。
- 应用前预览和摘要。

### Phase 3：整体应用到 ICity Base

目标：一键重建可被 iCity 使用的布局。

- 重建 Mesh。
- 初始化和继承属性。
- 刷新道路和城市。
- Undo 和备份。
- Blender 手动验收。

### Phase 4：草图识别

目标：将简单草图转换为可编辑草稿。

- 确定依赖策略。
- 实现图像预处理和骨架提取。
- 生成 LayoutGraph。
- 进入 Phase 2 的统一规范化流程。

### Phase 5：局部修改和交互绘制

目标：提升编辑效率，但不作为第一版交付前提。

- 二维视图直接绘制。
- 局部拓扑应用。
- 道路属性和街区属性编辑。

## 15. 风险与权衡

### 15.1 整体重建与局部编辑

整体重建：

- 优点：实现清晰、结果确定、易于测试。
- 缺点：难以无损保留所有局部自定义属性。

局部编辑：

- 优点：更接近用户在现有城市上修改的直觉。
- 缺点：拓扑匹配、属性迁移和错误恢复复杂。

第一版建议整体重建。用户通过修改完整草稿后再次应用来完成“修改布局”。

### 15.2 任意道路图与建筑生成限制

道路图算法可以支持任意平面直线图，但现有 iCity Geometry Nodes 未必支持所有街区面形状。模块应区分：

- 道路拓扑有效。
- 街区可被 Blender Mesh 表达。
- 街区可被当前 iCity 建筑节点正确生成。

不能将第三项未经验证地等同于前两项。

### 15.3 直线与曲线

第一版将道路表达为直线边。曲线道路需要额外定义采样、路口连接和街区边界语义，不应与基础点线功能同时引入。

### 15.4 草图识别可靠性

草图识别结果天然存在误差。因此必须坚持：

```text
识别结果 → 可编辑草稿 → 用户确认 → 应用
```

不能将草图识别设计为不可审查的一键覆盖。

## 16. 待讨论与决策

明日建议优先确认以下问题：

1. 第一版是否接受“应用时整体重建 `ICity Base`”，而不是局部无损修改？
2. 第一版是否只支持直线道路和二维平面道路？
3. 用户输入是否采用 JSON 为主，还是需要两个独立多行文本框？
4. 是否要求在 Blender 中直接点击绘制，还是列表、文本和预览已经满足课程需求？
5. 是否将“从当前场景读取并展示点线坐标”列为第一阶段独立交付？
6. 共线节点简化是默认自动执行，还是仅作为用户显式操作？
7. 对三角形、凹多边形等可能无法生成建筑的街区，是警告后允许应用，还是阻止应用？
8. 新街区默认全部生成程序化建筑，还是只创建面并由用户之后指定？
9. 草图识别是否允许引入 OpenCV 等外部依赖？
10. 草图输入只要求简单黑白线稿，还是还需要处理带道路宽度的手绘图？

12. 是否需要将候选非道路边 `Road del=True` 也纳入布局编辑器？

## 17. 第一版验收标准建议

第一版可交付标准建议定义为：

- 能读取当前 `ICity Base` 并展示所有节点坐标和边连接关系。
- 用户无需在 Blender 视图中直接选择顶点或边，即可修改完整道路图。
- 能导入和导出统一 JSON。
- 能正确处理近邻节点、交点、重复边和基础重叠线段。
- 能检测封闭街区并在应用前显示警告。
- 能整体重建 `ICity Base`，使道路、支持形状的建筑、交通和行人读取新布局。
- 草图识别结果进入同一草稿编辑流程，且不会未经确认直接应用。
